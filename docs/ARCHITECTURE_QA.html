CAT-Sim — Architecture Q&A

An in-depth walkthrough of the eight questions, grounded in the actual code. CAT-Sim is a consent-based phishing-simulation and cybersecurity-awareness-training platform; everything below traces a claim back to the file and mechanism that enforces it.

1What does the frontend handle, and what does the backend handle?

The short version: the frontend is a presentation layer with no secrets and no authority; the backend owns every decision that matters — auth, consent, persistence, email delivery, quiz scoring, and every privacy guardrail. If a rule protects a person, it lives in the backend and is pinned by a named test. The frontend is deliberately unable to break those rules even if it tried.

The repository is an npm-workspaces monorepo with two workspaces:

Frontend — frontend/ (React + Vite)

A single-page app served to the browser. A tiny hash-based switch in src/App.jsx selects one of four surfaces:

  • Public landing page (landing/) — marketing screen. Collects nothing: no form, no field.
  • Admin console at #/admin (admin/) — login, campaign CRUD & lifecycle, cohorts/consent, participant roster, the Send panel, and the analytics dashboard.
  • Public CAT learning site at #/learn (learn/) — lessons, resource library, and knowledge-check quizzes.
  • Enrollment / training view at #/enroll/<token> (enroll/) — where an auto-enrolled participant completes their training.

Its job is rendering, client-side routing, form UX, and calling the API over relative fetch('/api/...'). It holds a JWT in localStorage and puts it in an Authorization header. Sensitive inputs (the recipient roster, a raw participant address) live only in transient component state — never in localStorage, never in a URL.

Backend — backend/ (Express + PostgreSQL)

An Express API (with Knex over PostgreSQL) that owns all state and all sensitive logic:

  • Auth & roles — JWT login; two roles, program_admin and researcher, gated per route.
  • The data model — cohorts, participants, campaigns, interactions, modules, quizzes, assignments.
  • The guardrails — the consent gate, the campaign-status/pause gate, identifier hashing, discarding form bodies, keeping bodies out of logs, server-side quiz scoring, and k-anonymised analytics.
  • Participant-facing pages — the tracked link (/t), the server-rendered decoy sign-in page and disclosure (/sim, no client JS), and the training endpoints (/api/enroll).
  • Email delivery via a pluggable mailer.
  • In production it also serves the built SPA (single origin — see Q5).

A useful way to remember the split: the admin console can only ask the API to do things; whether they are allowed is decided server-side. For example, the console never has a "set consent = granted" edit — the client's own API wrapper omits it because the backend refuses to move consent through an ordinary PATCH (frontend/src/admin/api.js). And the quiz answer key is stripped server-side, so it never reaches the browser at all.

2Why did you choose React? What role does Vite play?

Why React

The centre of gravity in this product is the admin console — a stateful, multi-panel screen: a campaign list with lifecycle controls, a cohort/consent panel, a participant roster, a Send panel, an analytics dashboard, and a phase-comparison view. That is exactly the shape of problem a component model handles well:

  • Composability & local state. Each panel (SendPanel, CampaignAnalytics, ConsentControl, CohortPanel, ParticipantRoster, PhaseComparison) is a self-contained component owning its own state — including the deliberately transient roster in SendPanel that must never be persisted.
  • Testability. The frontend is covered by component tests (Vitest + Testing Library) sitting next to each component — SendPanel.test.jsx, ConsentControl.test.jsx, CampaignAnalytics.test.jsx, and so on. These pin behaviour like "the receipt is aggregate-only" and "Send is disabled unless the campaign is active" on the client side too, mirroring the backend.
  • A large, well-understood ecosystem for the learning site's content rendering and the two design systems (the "Civic" app system and the "Signal" marketing system, both documented in App.jsx).

Notably, the app is deliberately minimal about dependencies: routing is a hand-rolled hash switch (useHashRoute in App.jsx), not React Router, and the CAT site uses a small dependency-free, script-safe Markdown renderer rather than a heavy library. React gives the component/testing benefits without pulling in a framework.

What Vite does

frontend/vite.config.js

Vite is the frontend build tool and dev server. It plays three concrete roles here:

  1. Dev server with an API proxy. In development Vite serves the app on :5173 and proxies /api to the backend on :4000. Because the client calls the API with relative paths, this proxy is what lets it reach the backend without any CORS setup in dev — the browser sees one origin. 
    server: {
  port: 5173,
  proxy: { '/api': 'http://localhost:4000' },
}
  2. Production build. npm run build produces static, fingerprinted assets in frontend/dist, which Express serves in production (single origin — Q5). Vite fingerprints asset filenames, which is why app.js can cache them immutably while keeping index.html uncached.
  3. Test runner. The same config declares the Vitest setup (jsdom environment, setupTests.js), so unit tests and the app share one toolchain.
Deployment gotcha worth knowing Vite lives in devDependencies. Because the deploy sets NODE_ENV=production, a plain npm ci would omit Vite and the build would die on vite: not found. That is why the Render build command is npm ci --include=dev && npm run build — the --include=dev is required, not defensive.

3Show how the frontend sends a request to the backend and receives a response.

Every admin call goes through one wrapper in frontend/src/admin/api.js. It adds the bearer token, sets the content type, parses the JSON envelope, and normalises errors:

async function request(path, { method = 'GET', body, token = getToken() } = {}) {
  const headers = {};
  if (body !== undefined) headers['Content-Type'] = 'application/json';
  if (token) headers.Authorization = `Bearer ${token}`;

  const res = await fetch(`/api${path}`, {           // relative path → same origin
    method,
    headers,
    body: body !== undefined ? JSON.stringify(body) : undefined,
  });

  let payload = null;
  try { payload = await res.json(); } catch (_e) { payload = null; }

  if (!res.ok) {                                      // backend failure shape: { error }
    const err = new Error((payload && payload.error) || `request_failed_${res.status}`);
    err.status = res.status;
    err.code = payload && payload.error;
    throw err;
  }
  return payload;                                     // success shape: { data } / { token, admin }
}

The backend answers with a consistent envelope: { data: ... } (or { token, admin } for login) on success, and { error: "<code>" } with a non-2xx status on failure. The client maps a non-ok response to a thrown Error carrying .status and .code.

A concrete round trip: sending a campaign

The Send panel calls api.sendCampaign(id, recipients), which is just:

sendCampaign: (id, recipients, { resend = false } = {}) =>
  request(`/campaigns/${id}/send`, { method: 'POST', body: { recipients, resend } }),

Step by step:

  1. The client issues POST /api/campaigns/:id/send to the same origin, with Authorization: Bearer <jwt> and a JSON body { recipients, resend }. (In dev, Vite's proxy forwards /api to :4000; in prod the same Express process answers directly.)
  2. Express parses the JSON body (express.json()), and the request logger records only method/path/status/duration — never the body (Q7).
  3. The campaigns router runs requireAuth, then requireRole(program_admin) for the write section. A researcher's token is rejected here.
  4. The route calls sendCampaign(...), which enforces the campaign-status and consent gates (Q6), hashes each raw address to match a stored participant, and uses the address only as the mail recipient — persisting nothing.
  5. The service returns an aggregate summary (counts per outcome, withholding reasons), which the route wraps as { data: summary }. On a rule violation it throws an HttpError and the central error handler answers { error: "<code>" } with the right status (e.g. 409 cannot_send_from_draft).
One deliberate exception to the wrapper The analytics CSV export cannot be a plain <a href download>: the bearer token is a header credential and a link carries no headers, so the download would arrive as a 401. So fetchAnalyticsExport() uses fetch with the auth header and saves the returned blob. Same request pattern, just handling a binary body instead of JSON.

4Why did you choose PostgreSQL, and how are your database tables related?

Why PostgreSQL

The whole product rests on relational invariants that must hold at the data layer, not just in application code — and Postgres lets the schema enforce them:

  • Foreign keys with meaningful delete behaviour. A cohort can't be dropped while it still has participants (onDelete('RESTRICT')); deleting a campaign cascades to its interactions; deleting a module used by an assignment is restricted. These are integrity rules the DB guarantees.
  • CHECK constraints encode the state machines. cohorts.consent_status is constrained to pending | granted | withdrawn; campaigns.status to draft | active | paused | completed | archived; campaigns.enrollment_trigger to clicked | submitted; quizzes.pass_threshold to 0..100. Illegal values can't be written even by a buggy caller.
  • UNIQUE constraints back the guardrails. participants.email_or_phone_hash is unique (dedup, Q8); interactions(campaign_id, participant_id) is unique (one tracking token per target); training_assignments(participant_id, learning_module_id, campaign_id) is unique (idempotent enrollment — the enrollment service even relies on this to survive a race).
  • Native UUID primary keys via gen_random_uuid(), so IDs aren't guessable sequential integers.
  • JSONB for the quiz question bank (quizzes.questions), giving schema flexibility for the answer bank while everything else stays strongly typed.
  • Transactions and mature managed hosting (Render/Neon/Supabase), with TLS negotiated in production (knexfile.js).

Access goes through Knex: migrations under backend/migrations/ define the schema; a thin repository layer (backend/src/repositories/) wraps queries. The repositories are where the "no raw address ever reaches the DB" rule is physically true — participants.js hashes on the way in, and interactions.js has no method (and the table no column) able to hold a submitted value.

The schema itself is a guardrail — there is nowhere to put a submitted credential even if someone tried (pinned by schema.interactions.guardrail.test.js). This is why Q7 works.

5How did you deploy the application on Render, and what does render.yaml do?

render.yaml

render.yaml is a Render Blueprint — infrastructure-as-code. Rather than clicking services into existence, you commit this file and, in the Render dashboard, choose New → Blueprint → point at this repo. Render reads the file and provisions everything in it. The whole deploy is one step; there is no manual second stage.

What the file declares

Two resources: one web service and one Postgres database.

The database

databases:
  - name: catsim-db
    databaseName: catsim
    user: catsim
    plan: free

A free Postgres instance. (Caveat baked into the comments: Render deletes a free Postgres instance 30 days after creation — fine for a throwaway URL, not for a real study.)

The web service — build & start

buildCommand: npm ci --include=dev && npm run build
startCommand: npm run bootstrap && npm start
healthCheckPath: /health
  • Build: installs deps (including dev deps, because Vite is a dev dep and NODE_ENV=production would otherwise omit it — see Q2) and builds the SPA into frontend/dist.
  • Start: the free tier offers no pre-deploy command and no shell, so the schema can't be brought up as a separate manual stage. Instead npm run bootstrap (backend/scripts/bootstrap.js) runs at the start of every boot: it migrates every time, and seeds only a database that has never been seeded. Then npm start serves the API + SPA on $PORT.
  • Health check: Render polls /health to decide the instance is live.
Why the seed guard is load-bearing The seeds are destructive — 01_demo_data.js clears cohorts, participants and interactions before inserting. A free web service restarts every time it wakes from idle. An unguarded seed would therefore erase collected behavioural data on every cold start. SEED_ON_BOOT controls it: auto (default) seeds only an unseeded DB, never skips, force reseeds and discards data.

A committed value: console would silently reset a dashboard MAIL_PROVIDER=mailgun back to console and send every campaign through the no-op provider. Left unset, the code still falls back to console (so the default is still hermetic), while a value you set in the dashboard actually persists.

The deployment shape: single origin

CAT-Sim deploys as a single origin — one Node process serves the API and the built React app. This is not a preference: the client calls the API with relative paths and the Express app registers no CORS middleware, so a split frontend/backend deploy would fail in the browser on every request. app.js mounts frontend/dist when present and falls back to index.html for app routes, while leaving /api, /t, /sim and /health to their real handlers (so an unknown API path still 404s as JSON, not as the SPA document).

Single origin also collapses the two participant-facing base URLs (PUBLIC_BASE_URL for /t & /sim, APP_BASE_URL for the SPA's #/learn & #/enroll) into one host, so no origin overrides are needed.

Free-tier caveats to remember: the web service spins down after ~15 minutes idle (the first tracked-link click after a quiet spell waits out a cold start), and — by default — no email is sent (MAIL_PROVIDER=console), so a test send "succeeds" and shows a count yet nothing leaves the service.

6Where does the backend check consent and campaign status before sending an email?

There are two independent gates in the send path, checked in a fixed order: first campaign status (once, for the whole send), then consent (per recipient). Both live in backend/src/services/delivery.js, and consent routes through the single predicate in backend/src/services/consent.js.

Gate 1 — campaign status must be active

Before anything is hashed or matched, sendCampaign refuses a non-active campaign outright:

const campaign = await repos.campaigns.findById(campaignId);
if (!campaign) throw notFound('campaign_not_found');
// A campaign only sends while active. draft/paused/completed/archived all refuse.
if (campaign.status !== 'active') {
  throw new HttpError(409, `cannot_send_from_${campaign.status}`);
}

This is also why pausing a campaign is a real rollback: a paused campaign can't send. (The route in front of this, POST /api/campaigns/:id/send, is additionally gated to program_admin — a researcher can't even reach the handler.)

Gate 2 — every recipient must be deliverable (consent)

Inside the send loop, each matched participant is run through the one predicate that decides "may we contact this person":

// Consent gate — the single predicate. Fail closed.
const cohort = await repos.cohorts.findById(participant.cohort_id);
if (!isDeliverable(participant, cohort)) {
  summary.skipped.not_deliverable += 1;
  const reason = ineligibilityReason(participant, cohort) || 'not_deliverable';
  summary.ineligible_reasons[reason] = (summary.ineligible_reasons[reason] || 0) + 1;
  continue;   // never handed to the mailer
}

And the predicate itself (services/consent.js) is a pure, fail-closed function — a participant is deliverable only when their cohort's consent is granted and they have not individually opted out:

function isDeliverable(participant, cohort) {
  if (!participant || !cohort) return false;
  if (participant.opted_out === true) return false;
  return isCohortConsented(cohort);           // cohort.consent_status === 'granted'
}

Why it's structured this way

  • One source of truth. Both sendCampaign (Phase 5) and notifyEnrollments (Phase 8, the "you've been enrolled" email) call the same isDeliverable predicate. There is no second, divergent copy of the consent rule, and no code path that mails around it — pinned by delivery.guardrail.test.js.
  • Fail closed. Any missing input, un-granted cohort, or individual opt-out returns false. Consent is never granted by omission.
  • Defence in depth on the recording side. A separate gate, services/campaignState.js, governs whether a paused campaign records new behavioural flags or triggers enrollment on the participant-facing routes (/t, /sim, enrollment). That gate is deliberately fail-open (it governs behavioural flags, not a legal-safety guardrail, so a transient lookup hiccup never drops a live campaign's data) — the opposite stance from the consent gate, which fails closed. The enrollment service checks campaign status too, so no enrollment can be created for a halted campaign even via a direct call.

7Show how the system records a submission without storing the values entered. Could those values appear in logs?

When a participant "submits" the decoy login form, the backend records the single boolean submitted = true and discards every posted value. And no — those values cannot reach the logs, because the logger is built to never read a request body, query string, or headers.

How the submission is recorded

backend/src/routes/sim.js — the POST /sim/:token handler is the single most sensitive path, and it is written to never touch req.body:

router.post('/:token', asyncHandler(async (req, res) => {
  const interaction = await findInteraction(req.params.token);
  if (interaction && !(await isRecordingHalted(interaction))) {
    const updated = interaction.submitted
      ? interaction
      : // No value argument — there is nothing to persist beyond the boolean.
        (await interactions.markSubmitted(interaction.id)) || interaction;
    await safeEnrollFromInteraction(updated);       // best-effort side effect
  }
  // 303 → force a GET on the disclosure page, and never echo the body back.
  res.redirect(303, disclosurePath(req.params.token));
}));

The write it performs, interactions.markSubmitted(id), takes no value argument by design:

// Records THAT the dummy form was submitted. Deliberately accepts no field values.
async function markSubmitted(id, at = new Date(), trx) {
  return repo.update(id, { submitted: true, submitted_at: at }, trx);
}

This is defended in three layers, so it can't quietly regress:

  1. The route never reads req.body.
  2. The repository has no method that accepts a submitted value.
  3. The schema has no column that could hold one (Q4). Pinned by schema.interactions.guardrail.test.js and sim.form.guardrail.test.js.

Every submission then redirects (303) to the disclosure page — which renders even for an unknown token — so a participant always learns it was a simulation (transparency guardrail). The decoy pages are server-rendered with no client JavaScript, so nothing on the page can exfiltrate what was typed either.

Could those values appear in logs?

No. The request logger in backend/src/middleware/requestLogger.js is built around an allow-list of safe fields and is structurally unable to serialize a body:

const record = {
  method: req.method,
  // req.path excludes the query string; use it (not req.originalUrl)
  // so tokens/values in query strings are never logged either.
  path: req.path,
  status: res.statusCode,
  durationMs: Math.round(durationMs * 1000) / 1000,
};
// req.body / req.query / req.headers are intentionally NOT read.

The other places output is produced are equally careful:

  • Central error handler (app.js) logs only request metadata plus the error's own stack/message — messages our own code controls — and only for 5xx. It never echoes the body back to the client and never logs 4xx client validation.
  • The mailer re-throws provider errors in exactly one safe shape (mailer: <provider> send failed (<code>)), a status/errno only. Delivery's safeFailureReason trusts only that shape and buckets anything else as a generic send_failed, so a provider message that happened to echo a recipient address never lands in the summary or a warn line.
Honest nuance Express does parse the JSON/urlencoded body into req.body in memory (express.json() runs for all routes, because ordinary API routes need their bodies). The guarantee is not "the body is never parsed" — it's that nothing ever persists or logs it: the sim route ignores it, the logger can't read it, and it's discarded when the request ends. This whole property is re-verified end-to-end by system.credential.audit.test.js, which drives the integrated loop and proves no submitted value or raw address escapes through logs, traces, response bodies/headers, or the store.

8How do keyed email hashes work, and how can you match recipients without storing their email addresses?

The system never stores a raw email or phone number. It stores a keyed HMAC-SHA-256 digest of the normalised address. Because the same address always produces the same digest, you can match a recipient by hashing the address you already hold and looking up that digest — but you can't run the digest backwards to recover the address.

The hash

backend/src/lib/hash.js

function normalizeIdentifier(raw) {
  return String(raw).trim().toLowerCase();     // case/space variations collapse to one identity
}

function hashIdentifier(raw, secret = config.identityHashSecret) {
  if (raw == null || String(raw).trim() === '') throw new Error('identifier is required');
  return crypto
    .createHmac('sha256', secret)              // KEYED — not a bare hash
    .update(normalizeIdentifier(raw))
    .digest('hex');
}

Two properties make this work:

  • Keyed (HMAC with IDENTITY_HASH_SECRET), not a plain SHA-256. Email addresses come from a small, guessable space — a bare hash would fall to an offline dictionary attack (hash every address in a leaked list, compare). Keying with a secret the attacker doesn't have makes that infeasible. This is why render.yaml generates the secret per service and never commits it, and why rotating it invalidates every stored hash (a breaking change).
  • Deterministic. The same normalised address always maps to the same digest, so the digest is a stable pseudonymous key — usable for de-duplication and for per-participant linkage in the enrollment loop.

What's stored

backend/migrations/…_create_participants.js — the participant row carries a hashed identifier and no raw column by design:

table.string('email_or_phone_hash').notNullable().unique();   // hashed only
// there is deliberately no `email` / `phone` column
table.string('role');
table.string('department');
table.boolean('opted_out').notNullable().defaultTo(false);

The unique constraint is what makes the digest usable for dedup: one participant per address.

How matching works without the address on file

The raw address is supplied transiently at send time by the admin's roster (in the request body, which the logger never reads — Q7), and it's matched by hashing it and looking up the digest. From backend/src/repositories/participants.js:

async function findByIdentifier(identifier, trx) {
  // hash the raw address, then look up by the stored digest
  return repo.findWhere({ email_or_phone_hash: hashIdentifier(identifier) }, trx);
}

So the delivery loop (Q6) does this per recipient:

  1. Take a raw address from the transient roster.
  2. findByIdentifier(raw) → hash it → look up the participant by digest. No match → counted as skipped.unknown, nothing stored.
  3. Run the matched participant through the consent gate.
  4. Use the raw address only as the mailer's to field — then let it fall out of scope. It is never written to any table or log.

The trade-off, stated plainly

This is pseudonymisation, not anonymisation, and that's the intended design. You can go address → digest (that's how matching, and the POST /api/participants/lookup endpoint for handling an opt-out request, work), but you cannot go digest → address. An attacker who steals the database gets a table of opaque HMAC digests with no key, so they can't recover who the participants are; and even a legitimate operator can't produce a roster of real addresses out of the stored data. The address only ever exists in memory for the moment of a send. That is the whole point of guardrail #6 (data minimisation) — the system is built not to be able to answer "which of my staff is at address X" from its own storage.
